## Auto-Selection Architecture

### Composite Scoring Formula

```
score = (
    quality_score * 0.30 +       # Base data quality (8 metrics)
    fitness_score * 0.40 +       # CCM-specific fitness (role-dependent)
    confidence_numeric * 0.20 +  # Modeling confidence (10/7/3/1)
    (coverage_pct / 100) * 0.10  # AOI coverage (0–1)
)
```

**Result:** 1–10 numeric score per candidate per role

**Threshold:** Score < 5.0 → "MANUAL_SELECTION_REQUIRED"

### Tie-Breaking Strategy

When candidates have equal scores:
1. Role precedence (DEM > Extent > Vehicle > Soil > Vegetation > Hydrology > Contours)
2. Alphabetical name (deterministic, reproducible)

### Recommendation Output Structure

```json
{
  "role": "DEM",
  "recommended": "ASTER_30m.tif",
  "score": 7.8,
  "metrics": {
    "quality": 8,
    "fitness": 8,
    "confidence": "High",
    "coverage_pct": 95.0
  },
  "alternatives": [
    {
      "name": "SRTM_30m.tif",
      "score": 6.2,
      "reason": "Geographic CRS; requires reprojection"
    },
    ...
  ],
  "reason": "ASTER_30m: Quality 8/10, Fitness 8/10, 95% coverage, High confidence",
  "user_override": null
}
```

- Works without arcpy (uses pure Python header parsing)
- Enhanced metadata reads when arcpy available
- Handles missing/malformed data without crashing

### ✅ Backward Compatible
- v0.57 catalog JSON format unchanged
- Existing project config preserved
- Can downgrade: v0.58.1 outputs ignored if running v0.57

### ✅ User-Controllable
- User can override any recommendation in Step 1
- Alternatives listed for each role (top 2 runners-up)
- No automatic substitution without user approval

### ✅ Auditable
- Every score includes reasoning text (not just numbers)
- JSON output at every phase (quality, fitness, confidence, readiness, recommendations)
- HTML report styled for archival + sharing

### ✅ Deterministic
- Same data → same recommendations (reproducible)
- Tie-breaking via precedence + alphabetical sort (not random)
- Thresholds published in code (not magic numbers)

### Scoring Process

**Quality Phase:**
- ASTER_30m: temporal=10, CRS=10, coverage=8, resolution=6 → avg=8.0
- SRTM_30m: temporal=7, CRS=5 (geographic), coverage=6, resolution=6 → avg=6.0

**Fitness Phase (DEM):**
- ASTER_30m: raster=3, void-free=3, resolution=2, accuracy=1 → 9.0
- SRTM_30m: raster=3, void-free=2 (SRTM void-filled), resolution=2, accuracy=0 → 7.0

**Confidence Phase:**
- ASTER_30m: (8+9)/2=8.5, coverage=95% → "High"
- SRTM_30m: (6+7)/2=6.5, coverage=75% → "Moderate"

**Recommendation Phase (DEM role):**
```
ASTER: (8.0 * 0.30) + (9.0 * 0.40) + (10 * 0.20) + (0.95 * 0.10) = 8.36
SRTM:  (6.0 * 0.30) + (7.0 * 0.40) + (7 * 0.20) + (0.75 * 0.10) = 6.61
```

## Design Rationale

### Why Weighted Composite Scoring?

Simple max(quality, fitness, coverage) would miss the NG-NRMM workflow:
- A dataset with perfect quality but poor CCM fitness (e.g., wrong USCS soil codes) would mislead
- Fitness 40% weight emphasizes role-specific suitability over raw data quality
- Confidence 20% weight adds modeling confidence without inflating good-quality-bad-fit candidates
- Coverage 10% is a tiebreaker (all else equal, wider coverage wins)

### Why User Override?

Auto-selection can miss domain knowledge:
- Analyst may have field experience validating a lower-ranked candidate
- Data may have been hand-calibrated against ground truth (not reflected in metadata)
- Project constraints may favor a specific source (cost, licensing, access)
- v0.58.1 recommends; analyst decides

### Why Three JSON Outputs?

Auditability + debugging:
- `ccm_quality_scores.json`: "Why did dataset X score 5.2 on quality?"
- `ccm_fitness_scores.json`: "Why is soil fitness only 3.0 for this GeoPackage?"
- `ccm_recommendations.json`: "Why is ASTER recommended over SRTM?"

Each file is complete + self-contained for offline review.
