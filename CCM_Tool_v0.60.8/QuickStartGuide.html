1.What is the CCM Tool?

CCM stands for Cross-Country Mobility. In one sentence: you give it a map of the terrain (elevation, soil, vegetation, water), pick a vehicle, and it draws a map answering "where can this vehicle drive, and how fast?"

The result is a speed surface — a polygon layer covering your study area where every polygon is colored by how fast the chosen vehicle can move through it, from full speed down to "No-Go" (impassable). From there you can ask follow-up questions: why is an area slow, how far can I reach in 30 minutes, which of two vehicles is better for this terrain, where are the hidden obstacles, and what's the fastest route from A to B.

You do not need to be a soil scientist or a GIS expert. The tool reads standard GIS data (rasters, shapefiles, feature classes) and does the geospatial modeling for you. This guide tells you, for every step, exactly what kind of file to point it at — and what to do if you don't have the "ideal" version of that data.

2.Before you begin

Three things to have ready:

1. ArcGIS Pro, licensed and signed inThe toolbox runs inside ArcGIS Pro. Most steps need ArcPy, which only works once you've opened ArcGIS Pro and signed in with a valid license.
2. Anaconda Prompt (for setup/verification only)Used once to set up the Python environment and run the test suite. You do not need it to actually use the toolbox day-to-day — that happens inside ArcGIS Pro.
3. A folder for your projectPick (or create) one empty folder on your drive. Every step below points at this same folder — the tool organizes everything inside it automatically.

Setup, once:

CCM_anaconda.bat
RUN_TESTS.bat

This creates the ccm_tool Python environment and runs the built-in test suite to confirm your copy of the tool is healthy. Then, in ArcGIS Pro: Catalog pane → right-click Toolboxes → Add Toolbox → select CCM_Tool_v0.60.1.pyt. You should see six tools appear: Step 0, Step 0b, Step 1, Step 2, Step 3, Step 4.

The one idea that makes everything else click: every step below shares a single Project Root Folder. Pick one folder, point every step at it, and the tool automatically creates and reuses a standard layout inside it — you never have to remember separate output locations per step. 
<Project Root Folder>/
    ccm_project.json      (the tool's memory — written automatically)
    01_Input_Data/         (put your source data here, in any subfolders)
    02_Scan_Index/          (Step 0b's reports land here)
    03_Project.gdb          (the project's ArcGIS geodatabase)

4.Step 0 — Load MGCP Data

0

Load MGCP Data

Optional
Skip this entirely unless your source data is specifically in MGCP military format.

What it does

MGCP (Multinational Geospatial Co-production Program) is a military terrain-data standard that packages many feature types (roads, hydrography, vegetation, soil, elevation cues) together using FACC codes. Step 0 reads MGCP source files and consolidates the feature classes you want into one clean output geodatabase, so the rest of the toolbox can use them like any other GIS data.

When to use it / when to skip it

Use it if your data comes from an MGCP GeoPackage, File Geodatabase, or a folder of MGCP-schema shapefiles. If your data is "normal" GIS data (a DEM you downloaded, a soil shapefile, a land-cover raster), skip Step 0 — go straight to Step 1, which reads that kind of data directly.

What it needs

Data types this step accepts
InputAccepted formatsAlternates / notes
MGCP source dataGeoPackages (.gpkg), File Geodatabases (.gdb), or a folder of shapefiles (optionally searched recursively)Mix and match any combination of the three; leave "Feature Classes to Import" and "Themes to Import" blank to import everything
Output locationAn Output Geodatabase, or a Project Root Folder (recommended — keeps everything in the standard layout)Point Step 0 at the same Project Root Folder you'll use for every later step
Coordinate systemOptional — reprojects on import if setIf a source has no defined CRS, the tool can assume WGS84 (EPSG:4326) rather than fail

Output

A consolidated file geodatabase of clean feature classes, plus (if you used the Project Root Folder option) a manifest file that Step 1 can read automatically so you don't have to re-select the same data.

5.Step 0b — Data Intelligence Scan

0b

Data Intelligence Scan

Optional — recommended
Answers "what data do I actually have, and is it any good?" before you commit to Step 1.

What it does, in plain language

Point Step 0b at a folder of GIS files and it reads through everything, in plain terms, and tells you: what it thinks each file is (a DEM? a soil layer? vegetation?), how fine or coarse it is, whether it actually covers your study area, and whether anything important is missing. It then scores each candidate dataset for quality, fitness for its role, and confidence, and writes out a reviewable set of recommendations for Step 1.

Important: it never picks for you. Step 0b only makes suggestions. Step 1's own explicit settings always win — Step 0b's recommendations are a starting point you can accept or override, never an automatic substitution.

When to use it / when to skip it

Worth running any time you're not 100% sure what's in a data folder, or want a sanity check before a long Step 1 setup — especially useful the first time you inherit a data drop from someone else. If you already know exactly which files you want and their locations, feel free to skip straight to Step 1.

What it needs

Data types this step accepts
InputAccepted formatsAlternates / notes
Project Root FolderThe same shared project folder — put source data anywhere under its 01_Input_Data/ subfolder (or directly in the root if that subfolder doesn't exist yet)This is the only required input
Analysis ExtentOptional polygon feature class of your study areaWithout it you still get the full inventory; with it you additionally get a % coverage figure per dataset

Step 0b recognizes the same broad categories of data described in the cheat sheet below — DEM/elevation, soil, vegetation/land-cover, hydrology, contours, MGCP, vehicle CSVs, and coordinate/extent files.

Output — all written to <Project Root>\02_Scan_Index\

CCM_Data_Intelligence_Report.htmlOpen this in any browser — the human-readable factual inventory
CCM_Recommendations_Report.htmlHuman-readable, reviewable suggestions for Step 1
ccm_data_catalog.jsonMachine-readable inventory
ccm_quality / fitness / confidence / readiness_scores.jsonThe underlying scoring detail, if you want to dig in

6.Step 1 — Project Setup & Pre-process

1

Project Setup & Pre-process

Required — run once per project
The one-time data-entry step. Everything after this reuses what you set up here.

What it does

Step 1 is where you tell the tool what your actual data is. You point it at your elevation, soil, and vegetation data (raw or already-processed), your study area boundary, and a vehicle list. It converts everything into a consistent set of feature classes inside the project geodatabase and saves a memory file (ccm_project.json) — so Steps 2 and 3 never ask you for the same information again.

What it needs

Data types this step accepts, and what to do if you don't have the ideal one
InputAccepted formatsAlternates / notes
Analysis Extent (required)A polygon feature class marking your study area boundaryMust use a Projected CRS (e.g. UTM) — not plain latitude/longitude. If it's Geographic, reproject it first; the tool blocks with a clear error rather than silently producing wrong distances
Elevation (required — one of two)A DEM raster: HRDEM, LiDAR, CDEM, SRTM, ASTER GDEM, Copernicus DEM, ALOS AW3D30, or any generic DTM/DSM/DEM rasterNo DEM at all? Supply a pre-classified Slope Regions polygon feature class instead (with a field holding the slope value, in percent or degrees) — either input works
Contour Lines (optional)MGCP contour polylines, or any generic contour polyline layerImproves vegetation-height calibration; safe to leave blank
Soil data (required — one of two)SSURGO / STATSGO2 (US — tabular folder or gSSURGO .gdb), DSS / SLC Canada (.dbf component + layer + name tables), HWSD v2 Global (HWSD2.mdb Access DB), SoilGrids 2.0 Global (raster folder + depth layer), MGCP soil, or Generic (any feature class with sand/silt/clay %, texture class, or USCS code fields — auto-discovered by field name)Leave "Soil Data Source" on Auto-Detect and the tool figures out which of the above you gave it. Already have a finished soil layer? Supply it directly as the "Pre-processed Soil FC" and skip pre-processing entirely
Vegetation data (required — one of two)ESA WorldCover, NLCD (US), CORINE Land Cover, NASA GEDI canopy height, GLAD canopy height, Canada biophysical products (LAI/fCOVER), DMTI Spatial land cover (Canada), MGCP vegetation, or any generic land-cover raster (auto-classified by keyword)Already have a finished vegetation layer? Supply it directly as the "Pre-processed Vegetation FC" and skip pre-processing
Hydrology layers (optional)Polygon feature classes for water bodies and riversImproves later obstacle/barrier detection in Step 3; safe to leave blank
Vehicle Definitions CSV (required, but defaulted)A CSV listing vehicles with their VCI (Vehicle Cone Index) ratings, in the Vehicles_Can.csv schemaA working default ships with the tool, so you're never blocked on this — supply your own CSV in the same schema to model different vehicles
MGCP Manifest (optional)The mgcp_manifest.json written by Step 0Only relevant if you ran Step 0 first; otherwise ignore
Data Root Folder (optional convenience)A folder the tool scans to try to auto-fill the fields aboveA time-saver, not a requirement — you can always set each field by hand

One more setting: Default Soil Moisture Condition

Pick dry, moist, or wet as the starting condition. Don't worry about getting this perfect here — Step 2 lets you change it (or pull live weather instead) every time you generate a map.

Output

Pre-processed soil and vegetation feature classes in 03_Project.gdb, plus ccm_project.json in the Project Root Folder recording every path and setting so Steps 2 and 3 auto-fill from here on.

7.Step 2 — Generate Mobility Map

2

Generate Mobility Map

Required
This is the step that actually produces the speed surface — the core output of the tool.

What it does

Using the data Step 1 prepared, Step 2 computes a speed surface: a polygon layer where every polygon is scored for how fast your chosen vehicle can move through it, all the way down to "No-Go" for impassable ground. It combines slope, soil trafficability (adjusted for moisture), and vegetation resistance into that single per-polygon speed value.

What it needs

Data types this step accepts
InputOptionsAlternates / notes
Project Root FolderSame folder as Step 1Everything else on this list auto-fills from ccm_project.json
VehicleChosen from a dropdown built from your Vehicle Definitions CSVRun Step 2 again with a different vehicle any time — it doesn't consume or change your Step 1 setup
Soil Moisture Conditiondry / moist / wet, or use Live Weather to fetch current rainfall for the areaNo internet access or weather API? Use a Manual Rainfall Override value, or just pick dry/moist/wet directly — live weather is entirely optional
Spatial Soil Moisture (optional, finer detail)A 3×3 grid of Open-Meteo points across the area for per-polygon moisture variation instead of one blanket valueLeave off for a simpler, faster run using one moisture value for the whole area
Stochastic P(GO) (optional)Monte Carlo mode — runs many randomized trials and writes a probability-of-GO field instead of a single yes/noOff by default; turn on if you want a confidence measure rather than a single deterministic answer
GO ThresholdA speed (km/h) at or below which a polygon is marked No-GoAdjust per mission — a slower vehicle or a more cautious mission profile might use a higher threshold

Output

A speed-surface feature class in 03_Project.gdb, symbolized and ready to view in ArcGIS Pro, with fields for speed (km/h), mobility category, and (if enabled) the stochastic P(GO) probability.

8.Step 3 — Advanced Analysis

3

Advanced Analysis

Optional — run any combination
Five independent follow-up tools that dig deeper into a speed surface you already generated in Step 2.

What it does

Step 3 is really five separate mini-tools bundled into one dialog. Turn on as many as you need — none of them depend on each other, and most of their inputs auto-fill from your project config.

A. Reason MapExplains why each area is slow or blocked — which single factor (slope, soil, vegetation) is the limiting one
B. Reachability Map (Isochrone)"How far can I get?" — draws rings showing everywhere reachable within 15, 30, 60, 120 minutes (you choose) from a start point
C. Vehicle CompareOverlays two vehicles' speed surfaces and highlights where one clearly outperforms the other
D. Obstacle DetectionScans for hidden barriers a speed surface alone might smooth over — slope breaks, narrow ditches, linear barriers
E. Waypoint RoutingFinds the time-optimal (fastest, not necessarily shortest) route from point A to point B

What it needs

Data types this step accepts
InputFormat / notesAlternates
Project Root Folder & Speed SurfaceAuto-filled from the project config once Steps 1 and 2 have runNothing to set up manually if you're continuing straight from Step 2
Start / End points (B, E)Type coordinates in any format: MGRS, Decimal Degrees, DMS, DDM, or UTMThe dialog shows the auto-converted equivalents in every other format live as you type — use whichever format you have on hand
Time Intervals (B)Comma-separated minutes, e.g. 15,30,60,120Any number of rings, any spacing
Contour / Hydro layers (D)Auto-filled from project config if you supplied them in Step 1Obstacle Detection still runs without them, using slope and the speed surface alone — results are just less refined
Two Speed Surfaces (C)Any two feature classes produced by Step 2 (or Step 4)Run Step 2 twice with two different vehicles first if you haven't already

Output

Each sub-analysis writes its own feature class or table into the project geodatabase — a Reason Map layer, isochrone polygons, a comparison feature class, an obstacle point layer, or a route polyline, depending on which you ran.

9.Step 4 — Compare Two Vehicles

4

Compare Two Vehicles

Optional — standalone shortcut
The same comparison as Step 3's "Vehicle Compare", but usable on its own without going through the rest of the toolbox.

What it does / when to use it

If you already have two speed-surface feature classes sitting in a geodatabase — maybe from earlier Step 2 runs, maybe from a different project — Step 4 lets you compare them directly without re-running Steps 1–3. It's a convenience shortcut, not a different calculation from Step 3's Vehicle Compare.

What it needs

Data types this step accepts
InputFormatAlternates / notes
Vehicle A & B Speed SurfacesAny two feature classes produced by Step 2, each with a name and a speed fieldThey don't need to come from the same project — as long as both cover the same area and use the same speed field name
GO ThresholdSpeed (km/h) below which a polygon counts as No-GoSet to match whatever you used in Step 2, or a new value for this comparison

Output

A single comparison feature class highlighting where Vehicle A outperforms Vehicle B, where B outperforms A, and where both agree.
